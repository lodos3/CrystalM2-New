# CrystalM2 — mechanics-first VFX audit (Warrior, Wizard, Taoist)

**Source checked:** `Shared/SpellCurriculum.cs`, `Shared/SpecialisationAbilities.cs`, `Shared/TalentAbilities.cs`, `Server/MirObjects/HumanObject.cs`, `Server/MirEnvir/Map.cs`, `Server/MirObjects/HumanObject.TalentActions.cs`, class particle renderers in `Client/MirScenes/`.

**Scope:** 70 legacy class spells + 11 signature/core class abilities + 57 talent abilities = **138 catalogue entries**. Legacy mechanism labels are summarised from the server's human-object dispatch and area-map handlers. Signature and talent descriptions are copied/summarised from the project's registered definitions, **not separately demonstrated by server-runtime tests**.

**Important:** This is an audit and implementation roadmap, **not a claim that all entries have received bespoke AAA graphics**. Entries labelled *audited* require subsequent focused implementation and visual verification. The uploaded source art currently has five 64×64 coverage masks packed into the Core assembly and resampled into the D3D atlas. More raw texture detail, depth-aware compositing and performance profiling are necessary before claiming AAA-level quality.

## Universal rendering rules

1. Mechanic determines origin, direction, targets, duration, and field lifecycle. Never select a visual solely from the spell name.
2. Named aimed runes **Soul Shield / Blessed Armour / Curse**: exactly one visual per successful cast at the chosen cell, show **above player, monster and scenery sprites**, independent of whether the debuff or friendly buff affects anyone.
3. Passive stat changes **do not emit looping circles**. Attach optional micro-cues to real attacks only.
4. For wards, the glyph outline is static. Thin flames, fine texture and embers **rise and disappear vertically from fixed stroke points**, with small lateral shimmer only.
5. AOE: a distinct cast-location warning and/or field; only target-specific feedback where mechanics warrant it. Preserve per-recipient buffs and debuffs without duplicating the main rune.
6. Melee: use actual weapon traces, direction and confirmed impact frames. Distinguish blade cuts, lightning and fire at contact.
7. Avoid empty untextured orbs, large halos, over-bloomed billboards, identical temporal phases, and fixed single-colour sprites. Limit dynamic light and particle budgets for crowded scenes.
8. Use F12 spell glow, cutoff, pass mode and blending on authored coverage particles. Preserve depth tests for ordinary hits while exempting only specifically foreground-targeted runes.
9. Changes to visual packets must not change gameplay damage, buff values, target selection or server timing. Failed or resisted spells may still produce casting visuals.

The submitted `.gdshader` scripts are **Godot-specific**; porting their actual math requires analysis and rewriting for `Client/Data/Shaders/World.hlsl` and direct tests in D3D11. They have not been compiled or integrated as HLSL in this pass.

## Validation checklist

- Run `dotnet build Client/Client.csproj -c Release` and `dotnet build Server.MirForms/Server.csproj -c Release`.
- Run `dotnet run --project Tests/ModernRendererTests/ModernRendererTests.csproj -c Release` and `dotnet run --project Tests/TaoistParticleTests/TaoistParticleTests.csproj -c Release`.
- Cast all three named runes at empty tiles and densely occupied tiles, with target lock on/off; verify one foreground rune, while correct buffs/debuffs remain.
- Cast Curse with repeated attempts where debuff fails; rune still animates but target attributes stay unchanged.
- Freeze two frames of each protective rune: glyph geometry does not translate; flame X roots remain near their source and Y moves upwards with alpha decay.
- Inspect night/day, bloom off/on, Glow Only, additive/screen and F12 cutoff edge cases.
- Inspect crowded scenes for clipping, light bleed, GPU spikes and texture atlas fallback; only then sign off on runtime/AAA visual results.
